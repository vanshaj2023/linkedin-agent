● Here's how the full job-scraping and auto-apply flow works, and how to run it:

  ---
  Architecture

  Two agents handle jobs:

  1. job_hunter_run (cron: 3x daily at 8am, 1pm, 7pm): scrapes LinkedIn jobs,
  LLM-scores them, sends Slack alerts for high-scoring ones, triggers referrals.
  2. auto_apply_run (cron: every 2 hours): scrapes recent jobs, auto-applies via
  Easy Apply (score >= 75) or sends a Slack manual-apply alert (score 65-74).

  Both are Inngest functions, so they run via the Inngest dev server, not
  directly.

  ---
  Steps to run locally

  1. Set up your .env (copy .env.example, fill in):

  GROQ_API_KEY=...
  MONGODB_URI=...
  INNGEST_SIGNING_KEY=...
  INNGEST_EVENT_KEY=...
  SLACK_BOT_TOKEN=...

  # Your profile
  YOUR_NAME=Vanshaj
  YOUR_EMAIL=aggs1825@gmail.com
  TARGET_JOB_KEYWORDS=backend engineer,software engineer,python developer
  TARGET_JOB_LOCATIONS=India,Remote

  # Applicant details for Easy Apply forms
  APPLICANT_PHONE=+91...
  APPLICANT_YOE=2
  APPLICANT_ROLE=Software Engineer
  APPLICANT_RESUME_PATH=./resume.pdf
  APPLICANT_LINKEDIN_URL=https://linkedin.com/in/yourprofile

  DRY_RUN=false   # set true to test without actually applying

  2. Start the FastAPI server:

  uvicorn main:app --reload --port 8000

  3. Start the Inngest dev server (in a separate terminal):

  npx inngest-cli@latest dev -u http://localhost:8000/api/inngest

  4. Trigger the functions manually (instead of waiting for the cron):

  Open the Inngest dev UI at http://localhost:8288, go to your functions, and
  click "Invoke" on:
  - job-hunter-run to scrape and score jobs
  - auto-apply-run to scrape recent jobs and queue Easy Apply

  ---
  What happens after trigger

  - Jobs are scraped from LinkedIn using your TARGET_JOB_KEYWORDS +
  TARGET_JOB_LOCATIONS
  - Each job is LLM-scored (Groq, llama-3.3-70b)
  - Score >= 75 + Easy Apply: queued for auto-apply via Playwright
  (browser/easy_apply.py)
  - Score 65-74: Slack alert sent to you for manual apply
  - Score < 65: stored as low_score, skipped

  The action queue processor (inngest_queue_processor) picks up the easy_apply
  actions and runs the Playwright browser automation.

  Key flag: DRY_RUN=true in .env means it goes through the whole flow but won't
  actually submit applications. Set it to false when ready to apply for real.

● The root cause is clear. Playwright uses async_playwright() which spawns a
  subprocess, and uvicorn on Windows uses SelectorEventLoop (which doesn't
  support subprocesses), overriding your policy set in main.py.

  The fix: run Playwright in a thread pool executor using asyncio.to_thread with
  the sync Playwright API, or wrap the call so it runs in its own event loop in
  a thread.

● Good news and a simpler fix than I started implementing. The root cause is
  clear: uvicorn is creating a SelectorEventLoop on Windows instead of
  ProactorEventLoop. The fix is a single flag.

  Stop your current server and restart with:

  uvicorn main:app --reload --port 8000 --loop asyncio

  The --loop asyncio flag tells uvicorn to use Python's built-in asyncio loop,
  which on Windows 3.8+ defaults to ProactorEventLoop (the one that supports
  subprocess spawning — which Playwright needs).

  The run_in_playwright_thread utility I added to browser/manager.py is still
  useful for running Playwright from non-uvicorn contexts, but you don't need to
  wrap every scraper function. The --loop asyncio flag fixes it globally.

  until the apply completes.
  - Manual apply jobs (score 65-74) send a Slack alert with buttons to mark as
  applied or trigger a referral.

  4. MongoDB
  - Every job found gets stored in db.jobs (from job_hunter_run) or
  db.recent_jobs (from auto_apply_run).
  - You can query these directly if you want to see everything regardless of
  score threshold.

  So the primary output is Slack. If you haven't configured SLACK_BOT_TOKEN and
  a channel, you won't see the alerts. Check your .env for SLACK_BOT_TOKEN and
  look at slack/bot.py to confirm which channel it posts to.

  The NotImplementedError errors should be gone. Here's a summary of what was
  wrong and what's fixed:

  Root cause: uvicorn's --reload spawns a child worker process. That child
  ignores the WindowsProactorEventLoopPolicy set in main.py and uses
  SelectorEventLoop, which can't spawn subprocesses (Playwright needs this).

  Fix applied: Every public function that calls async with async_playwright()
  now delegates to run_in_playwright_thread(), which runs the Playwright
  coroutine in a dedicated thread with its own ProactorEventLoop. This is immune
  to whatever loop uvicorn uses.

  Files changed: scrapers/jobs.py, scrapers/jobs_recent.py, scrapers/people.py,
  scrapers/feed.py, browser/easy_apply.py, agents/connection.py
